================================================================================
1. PRODUCT IDENTITY
================================================================================

Nexum is an AI-native personal financial intelligence system built by Lytrium.
It operates as a personal financial operating system: conversational, calm, precise, explainable and useful for daily decisions.

Nexum should help a user:
- register income and expenses naturally through chat or the application;
- understand available money, safe money and free money;
- track savings goals and required monthly progress;
- register obligations and identify pending commitments;
- understand credit-card debt correctly;
- receive useful, non-judgmental financial intelligence.

================================================================================
2. ARCHITECTURE
================================================================================

Nexum has migrated completely away from n8n to a robust, code-first architecture:

1. FastAPI Backend (Python)
   - Hexagonal Architecture (Router -> Service -> UoW -> Repository).
   - Fully typed with Pydantic.
   - Centralized authentication via Supabase JWT (PyJWKClient).
   - Modular domains (Users, Cash, Goals, Obligations, Credit, Intelligence, Conversations).

2. PostgreSQL Database (Aislada, gestionada via Supabase o Docker local)
   - Source of truth for financial math.
   - Enforces referential integrity (UUID PKs/FKs).

3. Google Gemini (AI Layer)
   - Natural Language Processing.
   - Function Calling (Tools) to extract structured financial intents.
   - NEVER performs financial arithmetic.

================================================================================
3. CURRENT MVP STATUS (ALPHA PRIVADA)
================================================================================

Backend is currently frozen at MVP Alpha Privada status.
All core financial transactions and AI integrations are operational, authenticated, and tested (100% test passing).

Frontend integration is the immediate next step.

================================================================================
4. DOMAINS AND CAPABILITIES
================================================================================

- Cash: Incomes, expenses, balances.
- Goals: Savings goals and contributions.
- Obligations: Recurring payments and their fulfillment.
- Credit: Credit card purchases and payments.
- Intelligence: Financial snapshot generation (available, safe money, velocity).
- Conversations: Multi-turn chat with intent extraction via Gemini.

================================================================================
5. AUTHENTICATION AND ONBOARDING
================================================================================

- Strict JWT perimeter using Supabase Auth.
- Onboarding requires calling POST /api/v1/users/me/bootstrap to sync the Supabase Auth User with the internal public.users table.
- All domains depend on CurrentUserProfile to resolve ownership via public.users.id.

7. FRONTEND PRODUCT PRINCIPLES
==============================

Nexum frontend must preserve the product philosophy:

* calm;
* premium;
* simple;
* precise;
* human;
* non-judgmental;
* financially explainable.

The interface should feel closer to Apple Health than to a traditional banking dashboard or trading terminal.

Avoid:

* dense dashboards;
* excessive metrics;
* aggressive colors;
* crypto aesthetics;
* hacker aesthetics;
* spreadsheet-first experiences;
* arbitrary insights;
* fabricated numbers;
* moralistic language;
* technical jargon exposed to the user.

The user should quickly understand:

* how much money is available;
* how much money is truly free to spend;
* which obligations are approaching;
* how goals are progressing;
* the current estimated credit-card situation;
* what requires attention.

================================================================================
8. FRONTEND LEGACY MIGRATION RULE
=================================

A legacy frontend already exists.

It contains UI, visual language, navigation patterns and components that should be preserved whenever they remain useful.

The frontend migration must:

1. inspect the legacy UI;
2. preserve valuable visual components;
3. remove obsolete n8n dependencies;
4. replace old integrations with the FastAPI backend;
5. avoid unnecessary redesigns;
6. improve only when improvement adds clear user value.

The objective is not to rebuild the product from zero.

The objective is to connect and complete the existing experience using the new backend.

================================================================================
9. FRONTEND INTEGRATION RULES
=============================

The frontend must use:

* Supabase Auth for signup, login, logout and session lifecycle;
* FastAPI as the application backend;
* a centralized typed API client;
* environment variables for backend URLs and public Supabase values;
* protected routes;
* loading, success, empty and error states;
* session refresh handling;
* onboarding guards.

The frontend must never expose:

* Supabase service-role keys;
* Gemini API keys;
* database passwords;
* private backend secrets.

The frontend must not perform critical financial calculations.

The backend and PostgreSQL remain the source of truth.

The frontend may format values for presentation, but it must not invent balances, debts, progress calculations or financial recommendations.

================================================================================
10. AUTHENTICATION AND ONBOARDING FLOW
======================================

Expected flow:

Signup or login
→ Supabase Auth session
→ retrieve access token
→ POST /api/v1/users/me/bootstrap
→ GET /api/v1/users/me
→ verify onboarding state
→ require first account creation when no accounts exist
→ load categories
→ enter dashboard

Important current limitations:

* A new user is born without accounts.
* A new user may not yet receive seeded categories automatically.
* The frontend must prevent the user from reaching a broken operational state.
* Do not invent a default account balance.
* Do not silently create fictional money.

================================================================================
11. CURRENT KNOWN ISSUES
========================

High priority:

1. Initial categories:

   * Determine whether global categories or per-user seeded categories will be used.
   * Until resolved, frontend onboarding must handle the absence of category data safely.

2. Initial account:

   * A user cannot register expenses correctly until at least one account exists.
   * Onboarding must require the creation of the first wallet/account.

Medium priority:

3. Rate limiting:

   * Backend currently lacks strict per-user AI usage limits.
   * This does not block frontend development but remains a backend hardening task before public launch.

4. Session lifecycle:

   * Frontend must handle expired JWTs, refresh behavior and redirects safely.

13. FINANCIAL DISPLAY RULES
===========================

The frontend must visually distinguish:

* exact values;
* estimated values;
* unavailable values;
* values pending user configuration.

Credit-card calculations that depend on statement-cycle assumptions must be labeled clearly as estimates when appropriate.

Never present internal estimates as official bank statement values.
